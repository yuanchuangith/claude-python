# GXP 根因分析共同规则

将问题现象、已提供的处理记录或只读排查证据整理为简明、可信、可执行的缺陷结论。人员姓名和记录日期不进入回填正文；业务功能名称、字段名称及必要的业务单号仍保留。“不需要名称”在此指处理人姓名，不是删除业务名称。

处理记录是可选材料，不是使用前提。用户可以只提供问题描述、操作过程、报错、业务单号或截图中的信息。没有处理记录不等于无法分析，也不等于尚未处理；依据实际可获得的证据判断。

## 先理解这次业务

根据本次材料或只读检查，弄清用户在办什么事、在哪一步做了什么、实际出现什么、按已确认业务要求应该怎样。还要区分填写错误、说明不清、显示不一致、功能异常和新提出的调整要求，不能把所有事项都写成程序故障。

- 复用会话中已经确认的业务要求；不知道的规则先查现有材料。只有关键规则仍缺失、会改变判断时才问一个具体问题，其余条目继续处理。
- 业务要求说明“应该怎样”，不能单独证明“为什么出错”。调整需求没有已确认故障原因时，直说“这是展示调整需求，目前没有确认功能故障原因”。
- 一项问题对应一条有依据的解释。历史案例和下面的示例只帮助组织语言，不能当作当前问题的调查结果。
- 材料前后矛盾时不要擅自拼成结论。例如“填错岗位却提示试卷错误”与“错误没有全部显示”不是同一件事，应写明还需要核对实际提示。

## 用业务人员能懂的话

正文面向不懂代码的业务人员，用“做了什么、哪里处理不对、因此出了什么问题”说明原因。保留用户页面上能看到的业务名称，避免要求读者理解程序如何实现。

- 不在三行正文中堆代码、表名、内部编号、节点位置或接口参数。技术证据用于支撑结论，只有用户另行要求技术详情时才展开。
- 尽量不用“渲染、字段映射、状态残留、幂等、校验依赖、生命周期”等术语。例如，证据确实表明旧列表被再次追加时，写“再次打开错误内容时，把上一次的内容又加了一遍，所以列表重复了”。没有该证据时不能照抄这句话。
- 原因不能只写“逻辑有问题”，办法不能只写“恢复正常”。用一句具体的话说明哪里做错、准备怎样处理，并保持原有业务含义。
- 简化语言不能补充事实。不擅自写“岗位没有员工”“员工已离职”“所有页面都受影响”“不会影响历史数据”等材料没有证明的结论。
- 业务术语中的限制条件要保留。例如“正常状态用户”不能改成“在职员工”或“有培训资格的人”；“该岗位”“本次导入”“指定版本”等范围不能省略。读起来通俗的同时，必须说的是同一件事。
- 没查清时写“待确认，目前只知道……，还需要检查……”。通常只写下一步最关键的检查，不罗列一串猜测供用户当结论使用。
- 用户提供了明确处理记录时写“根据提供的处理记录”；检查确认的事实才直接陈述。仅有“分页有问题”一类描述，即使来自处理记录，也仍不足以写出具体根因。

## 选择工作方式

- 用户要求“润色、整理、按格式输出”，且提供已有结论：直接整理材料，不为格式整理连接业务系统。按实际来源写“根据提供的处理记录”或“根据你的说明”，不能把口头说明说成处理记录，也不能声称已查证。
- 用户调用本技能分析问题，只有问题现象而没有处理记录或原因结论时：默认结合业务情况，复用下面的只读取证流程查找原因，不要求用户先提供处理记录或另说一次“排查”。用户明确要求仅整理现有材料、不查询系统时，尊重该限制。
- 从已有页面名称、操作、报错或业务单号着手定位。能通过现有材料和只读工具查到的信息自行查找；只有无法继续定位或关键业务要求不明确时，才向用户询问最少的必要信息，不要求补一份处理记录。
- 完成可行的相关检查后仍缺少关键证据，或取证受限时，根因写“待确认”并说明具体缺口。不能仅因没有处理记录便停止查证，也不能为了填满三项而猜出原因。
- 混合清单逐项处理，保留原始顺序和条目对应关系；不能将某一项的根因、修复记录或验证结果套到另一项。

## 复用只读取证

实际取证时，通过当前环境提供的技能目录或加载工具，读取 `gxp-lowcode-readonly:gxp-lowcode-debug`（原技能名 `gxp-lowcode-debug`）及该任务所需的引用文件。不依赖某台电脑的绝对路径，不固定插件版本号。只登记了技能名称不等于已加载正文，只看到了 MCP 工具名称也不等于查询成功。无法读取必要的排查规则或调用所需工具时，说明具体缺口，不虚构检查过程。

原技能负责证据获取、工具参数和诊断门禁；本技能负责用户要求的回填格式。沿用原技能的只读边界、紧凑读取、动作身份、发布版本、分支验证和源码升级规则。用户要求三行回填时，以本技能的三项正文替代原技能默认的完整技术报告，不因压缩格式降低确认根因的证据标准。用户另要完整证据或画布修改位置时，再按原技能报告规范提供。

- 不修改业务数据、页面配置、动作、草稿、发布状态或源码；不调用 `gxp-lowcode-editor`，不把“给出解决方法”视为实施授权。
- 不读取或输出数据库连接信息。优先使用原技能的结构化只读 MCP；兼容查询仅按原技能规定执行。
- 先区分实际现象、期望规则及无匹配时行为。业务记录编号只作为查找线索，不直接认作动作 code 或 RefId。
- 运行故障依据对应发布副本；历史故障匹配历史发布证据。开发库或本地快照不能代表生产状态，草稿修复和副本同步不能代表运行验证通过。
- 嵌套分支、字段过滤覆盖、跨动作调用及前后端实现问题，按原技能对应门禁补证据，不能凭节点名称或孤立代码片段判定根因。
- 原技能或必要工具不可用时，仍可整理已有材料，明确“待确认”及缺少的证据，不声称完成了系统取证。

## 结论与证据对应

每个问题在生成三行正文前，先整理本次可核查的证据对应关系；用户只要业务结论时，不把这份技术明细塞进正文：

- 业务事实：用户描述了什么操作、现象和期望。用户描述能证明其报告的情况，不能单独证明系统内部原因。
- 检查依据：引用本次实际读取的工具结果或材料位置，保留关联业务记录、环境、版本及结果是否完整。不得编造工具调用、检查结果或证据编号。
- 原因依据：指出哪些检查事实说明哪一步处理错误，以及这一步为什么会导致用户遇到的问题。仅搜索到相似代码、列出工具名称或拿到一个证据编号都不等于证明因果关系。
- 处理状态：明确是建议调整、用户反馈已调整、检查发现已调整，还是实际操作已验证；不同状态不互相替代。
- 范围依据：每个受影响页面或操作都对应检查结果或用户明确要求的调整范围，不从单页问题扩展成全部页面有问题。

检查结果跨版本、跨环境、记录不对应、返回截断或相互矛盾时，先补查相关缺口；缺口无法补齐的结论写“待确认”。不能把旧对话中的猜测或此前模型写出的结论当作新证据。

三行正文只能压缩和解释以上已支持的事实；改写为大白话时不能新增原因、受影响对象或修复成功的承诺。格式检查通过仅说明表达合规，不证明业务判断正确。

## 按证据决定说到哪一步

三行分别判断依据是否充分，不能因为一项已确认，就把另外两项也写成确定结论：

| 现有依据 | 可以怎样写 | 不能怎样写 |
| --- | --- | --- |
| 只有用户描述或截图 | “根据你描述的情况……”或“待确认……” | 将表现直接写成程序内部原因 |
| 有明确处理记录，尚未复核 | “根据提供的处理记录……” | “经检查确认……” |
| 查到了相关代码，但没确认本次是否用到 | 描述已查到的事实，并说明是否对应本次问题还需确认 | 把相似代码或草稿问题写成本次报错的原因 |
| 已确认本次操作涉及的错误处理及其后果 | 直接说明已支持的原因；更深层原因未知时到此为止 | 继续编造为什么当初会写错、谁遗漏了检查 |
| 只确认本次页面或操作出现异常 | “目前确认涉及……；其他页面尚未核查” | “所有页面受影响”或“只有该页面受影响” |
| 只有用户报告的页面范围 | “目前反馈涉及……” | 冒充已检查全部影响范围 |

仅发现当前配置与业务要求不一致，而历史报错缺少对应记录或版本时，分别说明当前问题与历史原因，不能将两者直接等同。一次查询没有结果、工具失败或结果不完整，都不能直接证明业务数据不存在。

原因未知时，解决方法只能写针对缺口的检查或有明确业务依据的调整目标；不能在这一行偷偷加入尚未确认的原因。已查清一部分时，保留那部分事实并指出缺口，不把整条退回毫无信息的“待确认”。

有多种解释都符合现有证据时，优先做能区分这些解释的最小只读检查。完成相关检查仍无法区分时停在待确认，不靠重复搜索相似案例提高确信程度。

## 根因与方案写法

根本原因说明“哪个环节或规则存在什么具体缺陷，如何造成当前现象”。必须区分用户提供的结论、已查证机制及待确认推测；现象本身不是根因。

- 不使用“分页有问题”“验证逻辑有问题”“错误重复渲染”等同义复述作为完整根因。
- 不从“每次点击数据翻倍”直接推定未清空数组；还可能涉及重复事件绑定、接口重复结果等。只有证据命中后才能确定具体机制。
- 不从显示不一致推断数据库映射错误；区分列标题、字段绑定、数据来源及需求调整。仅有统一展示要求时，根因可以写“目前是统一展示要求，是否还存在内容显示错误，需要核对各页面”。
- 有方案但缺根因时，不倒推一个确定根因。已修复说法也不等于已完成静态或运行复核。

解决方法说明“哪一步要怎样调整，调整后应该怎样”，与根因逐项对应。用“调整、补充、统一”等方案语气；未经验证不写“已修复”“已正常”。证据不足时写“先检查……，确认后……”而非直接要求修改某个猜测位置。用户明确说已经处理过时，按实际来源写“根据你的说明，已调整……，实际使用结果还需确认”或引用其处理记录，不抹去已处理事实，也不冒充验收。

影响范围说明“哪些业务、页面或操作涉及这次问题”。已知范围和待核查范围分开表述；不能因组件共用便声称全系统受影响。用户要求同时修改的查看、编辑和状态页面可以写“本次要求调整的范围”，未经检查不能当成已确认都存在故障。没有查到其他页面时也不能据此声称只有当前页面受影响。

## 常见问题的核查重点

以下仅为查证方向，不是预设根因或已确认修复方案：

| 问题 | 需要区分或确认的机制 |
| --- | --- |
| 年度培训开始培训报错 | 岗位与用户关联查询、正常状态筛选、结果判空及实际失败分支；不能仅因报错发生在开始培训便认定用户校验错误。 |
| 导入错误内容分页失效 | 页码与每页条数的变更事件、传参、数据切片或服务端分页、总条数和返回结果。 |
| 技能包字段与关联文件不匹配 | 名称、编号、版本对应的列标题、字段绑定及数据来源；按本次需求核对查看、编辑以及相关状态页面。 |
| 重复点击错误内容后列表累加 | 接口原始结果、追加或替换行为、弹窗状态生命周期和事件绑定次数。 |
| 模板中合格分值提示不完整 | 实际下载模板来源、该列的批注或校验提示与确认后的业务规则；不编造分值范围和必填条件。 |
| 仅岗位编号错误却提示试卷和分值错误 | 校验项依赖关系、条件分支、跨行或跨字段状态残留、错误归属及汇总映射；“误报”与“漏报”分别查证，不能用“输出全部错误”解释或修复误报。 |

## 固定输出

单个问题只输出三行，不加日期、姓名、问候或结尾邀请：

```text
根本原因：用大白话说明哪一步处理不对、为什么造成这个问题；不知道就写待确认。
解决方法：说明这一步要怎样调整；还没查清就说明先检查什么。
影响范围：说明涉及哪些业务、页面或操作，不扩大范围。
```

多个问题默认按原顺序分别使用“1. 问题简述”及上述三行。用户要求粘贴到表格单元格或不要标题时，每项仅保留三行，项间空一行；用户指定表格时按其列结构输出。

每项每行优先一到两句。必要的“根据提供的处理记录”“待确认”“实际使用结果还需确认”直接放入对应行，不另加状态栏目。三行正文不附技术定位块；用户需要时另行提供可核查的证据。不要暴露与该缺陷无关的业务记录或人员信息。

## 示例

输入已经明确提供“原程序未按岗位查询正常状态用户”的处理结论，仅要求整理时：

```text
根本原因：根据提供的处理记录，开始培训时，没有正确检查岗位下是否有正常状态的用户，导致判断结果不准确。
解决方法：按岗位查找正常状态的用户，再根据查询结果判断该岗位下是否有这类用户。
影响范围：根据处理记录，涉及年度培训的开启培训功能。
```

用户没有处理记录，但本次只读检查已确认“再次打开错误内容时，已有列表被追加了同一批内容”，且确认涉及岗位矩阵导入时，可写成下面这样。这是假设证据齐全的写法示例，不代表该问题已经查证：

```text
根本原因：再次打开错误内容时，把上一次已经显示的内容又加了一遍，所以点击后列表会重复。
解决方法：调整错误内容的显示方式，每次打开都显示本次完整的错误列表，避免重复加入已经显示的内容。
影响范围：岗位矩阵导入中查看错误内容的操作。
```

输入仅为“岗位编号填错，却同时提示试卷和合格分值错误”，且因工具不可用无法查证，或用户明确要求仅整理现有材料时：

```text
根本原因：待确认，目前只知道岗位编号填错后，试卷和合格分值也被提示有错，还没有查清原因。
解决方法：先检查这三项分别为什么被提示错误，确认原因后再调整，避免把没有填错的内容提示成错误。
影响范围：目前反馈涉及岗位矩阵导入时的内容检查和错误提示，其他入口尚未核查。
```

交付前逐项检查：不懂代码的人是否能看懂；是否符合这次业务和实际操作；每个原因是否有材料或检查结果支持；是否把猜测说成事实；处理办法是否针对原因；范围是否有依据；是否把“提示错了”与“提示少了”混为一谈；是否把准备处理或尚未验证写成已解决；三项是否齐全且不带姓名和日期。

修改本技能或接入其他 Agent 后，用 [acceptance-cases.md](acceptance-cases.md) 中的场景核对实际输出。它们是验收材料，不是历史业务事实；普通问题排查时不必加载。
